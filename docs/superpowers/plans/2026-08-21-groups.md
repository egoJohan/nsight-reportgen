## Reading notes — shape confirmed, one addition, one thing observed in flight

The controller's reading — a group holds members and per-customer `view`/`edit`
grants; effective access is a user's own grants plus every group they belong
to; groups are managed in Settings beside Users; per-user direct grants stay
in the backend but stop being the UI's day-to-day tool — is what this plan
builds. Nothing below silently redesigns that shape. Two things are worth
saying explicitly rather than leaving implicit:

**One addition beyond a literal reading: `merge_grants`.** Once a user's
grants can come from more than one place (their own record, and every group
they belong to), two sources can name the **same scope** with **different
modes** — a direct `view` grant on a customer and a group's `edit` grant on
that same customer, say. `permissions.py`'s `_best()` already picks the most
specific grant for a path, but among grants that tie on specificity —
including two grants naming the literal same scope — Python's `max()` keeps
whichever came first in the list, which is an accident of iteration order,
not a decision. Before groups existed this could not happen (a user's own
`grants` tuple is written wholesale by `set_grants`, never assembled from two
sources at once); once it can, "which list did the mode more permissive by
accident end up in first" is not something an admin should have to reason
about. Task 1 closes this with a small, pure, well-tested combinator. This is
the one place this plan adds something the controller's brief did not
literally ask for — flagged here rather than folded in silently.

**Where "effective access" is computed, and why not the obvious place.** The
obvious place to fold a user's group grants in is `Repository.get_user()` —
it is the one function every permission check ultimately reads through. It
is also the wrong place: `get_user()`'s return value is exactly what
`save_user()` writes back verbatim (`Repository.save_user` calls
`self.set_grants(auth, uid, user.grants)`), and `auth/users.py`'s
`set_admin()` round-trips a `User` straight through `save_user` on every
promote/demote (`updated = replace(user, is_admin=is_admin); repo.save_user(auth, updated)`).
If `get_user()` already blended in group grants, promoting or demoting
anyone who happened to belong to a group would silently copy that group's
grants into their own **direct**, permanent record — grants that would then
outlive the person leaving the group. This plan instead expands group
grants **only** in `auth/session.py`'s `resolve()`, the one place that
already sits between "the stored record" and "what a request is allowed to
do," and which already owns the 30-second cache (spec §7). `Repository.get_user()`
keeps its existing meaning — this user's own grants, nothing more — so every
existing caller (`routes_users.py`, `auth/users.py`, `auth/invites.py`,
`identity.py`) is completely unaffected, and `save_user` stays safe to
round-trip. See Task 3 for the full reasoning, embedded in the code itself.

**Observed while reading, not part of this plan.** At the time of writing,
the working tree carries **uncommitted** changes unrelated to groups: an
`AccessRequest` record and CRUD (`store/repository.py`, `store/paths.py`),
a `GET /customers/{id}/name` route and a `can_edit` field on
`GET /cases/{id}` (`api/routes_customers.py`), and frontend changes to
`ReportsSection.tsx`/`CaseDetailPage.tsx` — all part of an in-progress
"Manage permissions on the customer page" / "Request access" feature (commit
`ca177a4` plus further uncommitted work on top of it). This is a **different**
mechanism from groups — a signed-in user asking an admin for access to one
customer, decided as `granted`/`refused` — and this plan does not depend on
it, modify it, or reuse its names or paths (`Group` vs `AccessRequest`,
`LABEL_GROUP*` vs `LABEL_ACCESS_REQUEST`, `group_path` vs
`access_request_path` — no collisions). Because it is uncommitted and
evidently still moving, this plan's edits to `store/paths.py` and
`store/repository.py` are anchored on stable, unrelated landmarks (the end
of the file; `def _now()`; the `# --- fonts` section) rather than on exact
surrounding text that this other work may still be reshaping — re-read the
target file immediately before each edit rather than trusting the line
numbers quoted here. The baseline test count below was measured against the
working tree as it stood at planning time, including that in-progress work;
re-run the suite before Task 1's Step 2 to get a fresh number.

**Scope check.** This is not too large for one document. Six tasks: two
small, self-contained additions to files that already exist
(`merge_grants`; `effective_grants` + the `session.resolve` wire-up), one
new storage module section (`Group`), one new router, and two frontend
tasks that closely mirror `SettingsPage.tsx`'s existing Users tab — smaller
than `2026-08-21-users-and-invitations.md`'s ten tasks, and with no email,
no expiry, and no last-admin-style invariant to reason about. If a reviewer
wants it split anyway, the seam is exactly where the Users-and-Invitations
plan drew its own: Tasks 1–4 (backend, independently testable and
mergeable with the frontend untouched) and Tasks 5–6 (frontend, depends on
Task 4's routes).

**Goal:** Give nSight Studio group-based access management: an admin
creates a group, adds and removes members, and grants the group customers at
`view` or `edit` — the day-to-day way access is handed out, replacing the
per-user grant editor removed from Settings in `a114fce`. A user's effective
access is their own direct grants (still accepted by the API, per the
controller's brief, just no longer the UI's tool) plus the union of every
group they belong to, resolved on the same 30-second cache timescale spec §7
already promises for any other grant change. Admin stays a flag on the user,
never derivable from a group, enforced structurally by `Grant`'s own
constructor (it accepts only `"view"`/`"edit"`, nothing else — there is no
separate check to bypass).

**Architecture:** `Group` sits in `store/repository.py` next to `User` and
`Invite` — same sibling-file storage shape (`settings/group/{id}`,
`.members`, `.grants`), same tolerant-of-malformed-rows reading, same
alphabetical listing `list_customers` already uses. `permissions.py` gains
one pure combinator, `merge_grants`, with no I/O and no dependency on
`Group` at all — it just resolves what happens when two grant lists name the
same scope. `auth/session.py`'s `resolve()` is the one integration point:
after loading the stored user, it asks the repository for that user's
effective grants (their own, merged with every covering group's) and caches
the result exactly as it already caches everything else, so a group's grant
change, a membership change, or a group's deletion all reach a member within
the same window a direct grant already does. `api/routes_groups.py` mirrors
`routes_users.py`'s shape — `require_admin` throughout, wholesale-replace
semantics for both members and grants (`PUT /groups/{id}/members`,
`PUT /groups/{id}/grants`), the same tolerance for a grant naming a deleted
customer (shown, not hidden, ignored for access). The frontend adds one tab
to `SettingsPage.tsx`, reviving the exact customer-grant picker shape
`a114fce` removed from the Users tab — `useGrantableCustomers` was left in
place unused by that commit for exactly this reason.

**Tech Stack:** Python 3.13, FastAPI, pytest — no new backend dependency.
Frontend: React 19, TanStack Query 5, the existing `web/src/lib/surfaces.ts`
vocabulary — no new frontend dependency. No frontend test runner exists in
this repo; frontend tasks are verified with `cd web && npx tsc -b --noEmit`
plus a described manual check, matching every prior plan's own precedent.

### Task 1: `permissions.py` — `merge_grants` closes an order-dependent tie

**Files:**
- Modify: `src/reportbuilder/auth/permissions.py`
- Test: `tests/suite/unit/auth/test_permissions.py`

**Interfaces:**
- Produces: `merge_grants(*grant_lists: Sequence[Grant]) -> tuple[Grant, ...]`.

**Why this has to exist, precisely:** `_best()` picks the grant with the most
path segments among those covering a path. Among grants that **tie** on
segment count — including two grants naming the exact same scope string —
Python's `max(key=...)` keeps whichever appeared first in the sequence it is
given, because `max` only replaces its current answer on a **strictly**
greater key. A user with a direct `view` grant on `"attendo"` and a group
`edit` grant also scoped to `"attendo"` would get whichever mode happened to
land first in `user.grants` — an accident of how the two lists were
concatenated, not a decision anyone made. `merge_grants` resolves that once,
before the ambiguity can reach `_best`, by keeping at most one `Grant` per
scope and preferring `edit` wherever a scope is named more than once.

def merge_grants(*grant_lists: Sequence[Grant]) -> tuple[Grant, ...]:
    """Combine several grant lists into one, keeping AT MOST ONE Grant per
    scope — direct grants plus every group's, in practice (see
    store/repository.py's `effective_grants`).

    Why this exists, precisely: `_best()` above picks the grant with the
    most path segments; among grants that TIE on segment count — including
    two grants naming the exact same scope — Python's max() keeps whichever
    came first in the sequence it was given, an accident of concatenation
    order rather than a decision. A user with a direct "view" grant on a
    customer and a GROUP "edit" grant on that same customer must get edit
    either way, not whichever of the two happened to be read first. This
    resolves that tie ONCE, here, before the ambiguity can ever reach
    `_best`: the more permissive mode wins wherever a scope repeats: every
    scope keeps the order it was first seen in, so a scope that only ever
    appears once is otherwise untouched.
    """
    best: dict[str, Grant] = {}
    order: list[str] = []
    for grants in grant_lists:
        for g in grants:
            current = best.get(g.scope)
            if current is None:
                order.append(g.scope)
                best[g.scope] = g
            elif g.mode == EDIT and current.mode != EDIT:
                best[g.scope] = g
    return tuple(best[scope] for scope in order)
```

**Interfaces:**
- Consumes: `Grant`, `_new_id`, `_now`, `_natural_key`, `_write_json`/`_read_json` (all exist).
- Produces: `Group(id, name, member_ids, grants)`, `Repository.create_group(auth, name) -> Group`,
  `.rename_group(auth, group_id, name) -> Group`, `.get_group(auth, group_id) -> Group | None`,
  `.list_groups(auth) -> list[Group]`, `.set_group_members(auth, group_id, member_ids) -> None`,
  `.set_group_grants(auth, group_id, grants) -> None`, `.delete_group(auth, group_id) -> None`.

This task deliberately does **not** touch `get_user`, `session.py`, or any
route — a group can be created, named, populated and granted, and none of it
affects anyone's access yet. That wiring is Task 3, kept separate so the
storage shape can be reviewed on its own, the same way Plan for
Users-and-Invitations landed `Invite` storage (its Task 3) before
`identity.py` ever consumed one (its Task 5).

**Naming and uniqueness:** group names are **not** enforced unique.
`create_customer` sets no precedent for uniqueness either — a name is
metadata, an id is the identity ("Ids vs names" — `repository.py`'s own
module docstring) — and introducing a uniqueness rule for groups that
nothing else in this data model has would be a new invariant this plan was
not asked to add. Two groups named "Analysts" are distinguished by id, same
as two customers would be.

**Shape, and why it is not `_delete_prefix`:** a group has no descendants —
nothing else in datahive is addressed underneath a group the way a case is
addressed underneath a customer — so its deletion is `delete_user`'s
three-fixed-paths shape, not `delete_customer`/`delete_case`'s subtree scan.

        except (NotFound, ValueError, UnicodeDecodeError):

                # costs the group that one grant, not the whole record.

            return None

    def effective_grants(self, auth: AuthContext, user_id: str,
                         direct: tuple[Grant, ...]) -> tuple[Grant, ...]:
        """*direct*, plus the grants of every group *user_id* belongs to,
        merged so a scope named by both a direct grant and a group grant
        resolves to the more permissive mode regardless of which was read
        first (see permissions.merge_grants's own docstring for exactly
        why that matters).

        Called from auth/session.py's `resolve`, deliberately NOT from
        `get_user` itself: `get_user`'s return value is also `save_user`'s
        INPUT (auth/users.py's `set_admin` round-trips a User straight
        back through `save_user`, which writes `user.grants` to the DIRECT
        grants store verbatim). If `get_user` already blended in group
        grants, promoting or demoting anyone who happened to be in a group
        would silently copy that group's grants into their own direct
        record forever -- surviving even after they left the group.
        Keeping `get_user`'s contract at "this user's own grants, nothing
        more" is what keeps that round trip safe; this method is where the
        wider answer lives instead.
        """
        group_grants = [g.grants for g in self.list_groups(auth) if user_id in g.member_ids]
        return merge_grants(direct, *group_grants)

    def _leave_all_groups(self, auth: AuthContext, user_id: str) -> None:
        """Strip *user_id* from every group's member list. Groups store
        membership as a list of user ids (Group.member_ids) rather than
        the other way around, so nothing else notices a user is gone
        unless something goes and edits every group that named them --
        the same class of leftover `delete_user`'s password cleanup exists
        to prevent, on the other side of the relationship. Rewriting a
        group's `.members` sidecar is a plain `put`, never consent-gated
        (only `delete` is -- see `InMemoryObjectStore.put`/`delete`), so
        this can run unconditionally, first, with no retry loop."""
        for group in self.list_groups(auth):
            if user_id in group.member_ids:
                self.set_group_members(
                    auth, group.id, tuple(m for m in group.member_ids if m != user_id))

# src/reportbuilder/api/routes_groups.py
"""The Groups HTTP surface: create a group, manage its members and its
customer grants (docs/superpowers/plans/2026-08-21-groups.md — the base
design's spec §13 named "groups or teams" out of scope; this plan
supersedes that line at the controller's direction). Every route here is
require_admin, the same boundary routes_users.py draws -- administering
access is not itself a data grant (spec §5).
"""
from __future__ import annotations

from fastapi import APIRouter, Body, Depends, HTTPException
from pydantic import BaseModel, Field

from reportbuilder.api.deps_auth import require_admin
from reportbuilder.api.deps_store import get_auth, get_repository
from reportbuilder.auth.permissions import Grant, User
from reportbuilder.store.repository import Group, Repository
from reportbuilder.store.seam import AuthContext, ConsentRequired, NotFound

groups_router = APIRouter(tags=["groups"])


class NameBody(BaseModel):
    name: str = Field(min_length=1, max_length=200)


def _parse_grants(raw) -> tuple[Grant, ...]:
    """Same shape as routes_users.py's own `_parse_grants` -- kept local
    rather than imported, the way every routes_*.py file in this codebase
    owns its small request-shaping helpers rather than reaching into a
    sibling router module."""
    if not isinstance(raw, list):
        raise HTTPException(422, "grants must be a list")
    try:
        return tuple(Grant(g["scope"], g.get("mode", "view")) for g in raw if g.get("scope"))
    except (ValueError, KeyError) as exc:
        raise HTTPException(422, str(exc)) from exc


def _grant_out(repo: Repository, auth: AuthContext, g: Grant) -> dict:
    """Same shape as routes_users.py's `_grant_out` -- a grant naming a
    deleted customer or case is IGNORED for access (spec §5) but still
    SHOWN, with no name, so an admin can find and clear it."""
    parts = [s for s in g.scope.split("/") if s]
    customer = repo.find_customer(auth, parts[0]) if parts else None
    out = {"scope": g.scope, "mode": g.mode,
          "customer_name": customer.name if customer else None, "case_name": None}
    if customer is not None and len(parts) > 1:
        case = repo.find_case(auth, parts[1])
        out["case_name"] = case.name if case is not None else None
    return out


def _group_row(repo: Repository, auth: AuthContext, g: Group) -> dict:
    members = []
    for member_id in g.member_ids:
        u = repo.get_user(auth, member_id)
        if u is not None:
            members.append({"id": u.id, "email": u.email, "name": u.name})
    return {"id": g.id, "name": g.name, "members": members,
           "grants": [_grant_out(repo, auth, grant) for grant in g.grants]}


@groups_router.get("/groups")
def list_groups(auth: AuthContext = Depends(get_auth), repo: Repository = Depends(get_repository),
                admin: User = Depends(require_admin)) -> list[dict]:
    return [_group_row(repo, auth, g) for g in repo.list_groups(auth)]


@groups_router.post("/groups", status_code=201)
def create_group(body: NameBody, auth: AuthContext = Depends(get_auth),
                 repo: Repository = Depends(get_repository),
                 admin: User = Depends(require_admin)) -> dict:
    g = repo.create_group(auth, body.name.strip())
    return _group_row(repo, auth, g)


@groups_router.patch("/groups/{group_id}")
def rename_group(group_id: str, body: NameBody, auth: AuthContext = Depends(get_auth),
                 repo: Repository = Depends(get_repository),
                 admin: User = Depends(require_admin)) -> dict:
    try:
        g = repo.rename_group(auth, group_id, body.name.strip())
    except NotFound:
        raise HTTPException(404, f"Group '{group_id}' not found") from None
    return _group_row(repo, auth, g)


@groups_router.put("/groups/{group_id}/members")
def set_group_members(group_id: str, body: dict = Body(...),
                      auth: AuthContext = Depends(get_auth),
                      repo: Repository = Depends(get_repository),
                      admin: User = Depends(require_admin)) -> dict:
    if repo.get_group(auth, group_id) is None:
        raise HTTPException(404, f"Group '{group_id}' not found")
    raw = body.get("member_ids")
    if not isinstance(raw, list):
        raise HTTPException(422, "member_ids must be a list")
    member_ids = []
    for uid in raw:
        if repo.get_user(auth, uid) is None:
            raise HTTPException(422, f"User '{uid}' not found")
        member_ids.append(uid)
    repo.set_group_members(auth, group_id, member_ids)
    return _group_row(repo, auth, repo.get_group(auth, group_id))


@groups_router.put("/groups/{group_id}/grants")
def set_group_grants(group_id: str, body: dict = Body(...),
                     auth: AuthContext = Depends(get_auth),
                     repo: Repository = Depends(get_repository),
                     admin: User = Depends(require_admin)) -> dict:
    if repo.get_group(auth, group_id) is None:
        raise HTTPException(404, f"Group '{group_id}' not found")
    grants = _parse_grants(body.get("grants") or [])
    repo.set_group_grants(auth, group_id, grants)
    return _group_row(repo, auth, repo.get_group(auth, group_id))


@groups_router.delete("/groups/{group_id}", status_code=204)
def delete_group_route(group_id: str, auth: AuthContext = Depends(get_auth),
                       repo: Repository = Depends(get_repository),
                       admin: User = Depends(require_admin)) -> None:
    if repo.get_group(auth, group_id) is None:
        raise HTTPException(404, f"Group '{group_id}' not found")
    try:
        repo.delete_group(auth, group_id)
    except ConsentRequired as exc:
        # datahive gates destructive operations -- surfaced with its
        # approval envelope, same shape as remove_user_route.
        raise HTTPException(409, {
            "error": "consent_required",
            "message": "Deleting this group needs approval in datahive.",
            "request_id": exc.request_id, "target": exc.target,
            "approve": exc.envelope.get("approval_urls", {}),
        }) from exc


__all__ = ["groups_router"]
```

## Not in this plan

* **The `AccessRequest` / "Manage permissions on the customer page" work** —
  observed uncommitted in the working tree while reading, entirely separate
  from groups (a user asks for access to one customer; an admin decides).
  This plan does not touch it, depend on it, or reuse its names or paths.
* **Case-level grants in the Groups UI** — `PUT /groups/{id}/grants` accepts
  any valid `Grant` (customer or case), same as `PUT /users/{id}/grants`
  always has; the picker in Task 6 only offers whole customers, matching the
  scope the removed per-user `GrantPicker` already had ("Granting access —
  per customer").
* **Nested groups, or a group belonging to another group** — `Group.member_ids`
  names users only. Nothing in the controller's brief asked for this, and
  `merge_grants`/`effective_grants` would need real redesign to recurse
  safely (cycle detection, at minimum) if it were ever wanted.
* **Group-derived admin** — deliberately impossible, not merely unbuilt. See
  the reading notes and Global Constraints.
* **A per-request cache for `Repository.list_groups()`** — `effective_grants`
  lists every group on every cache-miss resolution (same cost model as
  `list_users`/`find_user_by_email`'s existing O(n) scans, not the ~60-per-report
  hot path spec §5.1 caches). At the scale this app runs at (tens of users,
  tens of groups, a 1-CPU hive) this is deliberately left unoptimized; if it
  ever becomes hot, the fix is the same per-request cache shape §5.1 already
  established, not a redesign.
* **Rate-limiting or auditing group changes** — not asked for, and an
  admin-only route behind a session is not the anonymous attack surface
  `/auth/register` is.

## Self-review

**Design questions, answered explicitly.**

* *Where effective grants are computed, and the caching story.* Task 3:
  `Repository.effective_grants` merges a user's direct grants with every
  covering group's, called from `auth/session.py`'s `resolve()` — the same
  place the existing 30-second cache already lives (spec §7). A group's
  grant edit, a membership change, or the group's own deletion all reach a
  member within CACHE_TTL_SECONDS, proven end-to-end in
  `test_sign_in_flow.py`'s two new tests, which mirror the existing
  direct-grant timing test exactly. `Repository.get_user()` is deliberately
  **not** where this happens — seeded in the reading notes, restated in
  Task 3's own docstring, and regression-tested directly
  (`test_saving_the_resolved_user_does_not_bake_group_grants_into_their_direct_record`).
* *A group's grants when the group is deleted.* Task 2's `delete_group`
  removes the group's `.grants`/`.members` siblings before the group's own
  record (retry-safe under `ConsentRequired`, mirroring `delete_user`'s
  documented ordering). Nothing else references a group by id, so nothing is
  left dangling; members' access follows on the same cache timescale as any
  other revocation.
* *Memberships when a user is removed.* Task 3's `Repository.delete_user`
  now calls `_leave_all_groups` first, rewriting every group that named the
  removed user — a plain, never-consent-gated write, so it costs no retry
  loop. Without this, a deleted user's id would linger in `Group.member_ids`
  forever, the same class of leftover the codebase's existing password
  cleanup exists to prevent, on the other side of the relationship. Tested
  directly in `test_repository_users.py`.
* *Whether a group can grant admin.* No, and it is structurally impossible,
  not merely policy: `Grant.__post_init__` accepts only `"view"`/`"edit"`,
  and a `Group`'s `grants` field is a tuple of `Grant` — there is no value
  that could name admin in the first place, so there is no separate check to
  write, forget, or bypass.
* *The last-admin rule.* Untouched. `auth/users.py` is not modified by this
  plan; admin remains a flag read from a user's own stored record
  (`d.get("is_admin")` in `Repository.get_user`), never touched by
  `effective_grants` or anything group-related.
* *Naming and uniqueness.* Not enforced, matching `create_customer`'s own
  precedent — see Task 2. A grant naming a deleted customer or case is
  ignored for access and still shown with no name, reusing `_grant_out`'s
  existing rule (spec §5) verbatim in `routes_groups.py`.

**Placeholder scan.** Every task's code is concrete, specific to that task,
and was written against the actual current contents of the files it
modifies (re-read at planning time, including the uncommitted, unrelated
`AccessRequest` work — see the reading notes). No "similar to Task N" stands
in for real code.

**Type consistency.** `Grant` (scope, mode ∈ {"view","edit"}) is the only
grant shape used throughout — `Group.grants`, `effective_grants`'s return
value, and every route response all carry it unchanged from Plan 1. `Group`
(the datahive record) and the `_group_row` dict a route returns are used
consistently: routes never leak a `Group` dataclass directly, the same
separation `Invite`/`_invite_out` already established.
`StudioGroup`/`StudioGroupMember` on the frontend match `_group_row`'s shape
field-for-field, and `StudioGroup.grants` reuses the existing `UserGrant`
type rather than inventing a parallel one, since `_grant_out`'s output shape
is identical either way.
